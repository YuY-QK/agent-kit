# 全局 AI 协作约定

本文件对我所有项目生效，由 agent-kit 安装到 Claude Code（`~/.claude/CLAUDE.md`）和 Codex（`~/.codex/AGENTS.md`）。它只放跨项目通用的习惯和底线。

项目根目录的 `AGENTS.md`、项目 `docs/` 中的权威文档，以及用户在当前任务中的明确要求，优先于本文件。

## 关于我

- 独立开发者，用 App 和小工具实现自己的想法；常用 Flutter 做移动端，也做单文件网页。
- 没有学过设计：界面和视觉方面，请主动提出方向和选项，说明理由，再让我选。
- 交流、文档、注释和提交说明默认使用简体中文，代码标识符用英文。

## 工作方式：先计划，再实施

- 新想法先完善成完整计划（想法简报、PRD、原型、技术设计、开发计划），确认后再实施；使用 `idea-to-plan` 技能。
- 小改动不需要走完整流程，但仍要先说清楚范围和完成标准。
- 一次推进一个阶段；每个阶段产出后停下来让我确认。

## 信息与决策优先级

1. 用户在当前任务中的明确要求。
2. 已确认的需求、验收标准和经用户批准的决策记录。
3. 当前代码、配置和自动化测试证明的已实现行为。
4. 技术说明、README、实施计划和发布清单。
5. AI 的推断与建议。

始终区分“当前实现”“目标要求”“建议方案”和“尚未确认的假设”。目标文档不代表已经实现；代码和测试证明当前行为，但不能自行改写已确认的要求。发现冲突时先说明冲突、影响和可选处理方式。

## 资料读取

- 先看项目 `AGENTS.md` 的“文档路由”，按任务范围读取最少且必要的章节；局部文案、样式或独立代码改动不必预读全部规则。
- 当前任务中已经读过的内容不重复加载。

## 默认工作流程

1. 检查相关代码、测试、文档和 `git status`，保护我已有的修改。
2. 明确当前行为、目标行为、范围、非目标、约束和可观察的完成条件。
3. 选择符合现有结构的最小完整方案；涉及产品或结构决策时先设计。
4. 只修改任务需要的文件，不顺手清理、升级依赖或重写相邻模块。
5. 按风险执行格式化、静态分析、测试、构建和人工检查。
6. 交付时说明改了什么、关键决策、验证证据、未验证项和剩余风险。

如果某部分依赖新的产品决策、正式接口、外部凭据、破坏兼容的迁移或超出授权的操作，只暂停这一部分并请我决定，其余已授权且可验证的工作继续完成。已经给过的授权无需重复确认。

## 文档约定

- 仓库内文档默认用 Markdown，放在 `docs/` 或相应专题目录；我明确要求时才生成 Word、PDF、表格或幻灯片。
- 规则和决定写在拥有它的权威文档里（需求在 PRD，技术在技术设计或 ADR），其他地方链接，不复制摘要。
- 需求、架构、数据契约、权限或交付范围变化时，同步更新对应的权威文档，再改代码。
- README 只描述真实可运行的方式和已有结构。

## 工程底线

- 名称表达实际意图；模块高内聚，函数目的清晰、抽象层级一致。
- 副作用放在明确的系统边界；错误可观察、可恢复，不静默吞错，不伪造成功。
- 未完成的能力要隐藏、禁用并说明条件，或展示真实的空/失败状态；不用 Mock、延迟动画或本地成功标记冒充已完成。
- 只为已出现的稳定共同概念做抽象，不为假设中的未来功能预建平台。
- 用明确类型表达状态、结果和错误，避免互斥布尔值、魔法字符串和特殊 `null`。
- 注释解释约束、原因和取舍，不复述代码；临时规避写明退出条件。

## 验证与报告

- 使用项目规定的工具链和命令（见项目 `AGENTS.md` 或 `docs/AI_RULES.md`）。
- 先跑与改动直接相关的检查，再按风险扩大；可能争用资源的构建不要并发执行。
- Bug 修复原则上增加能在旧实现上失败的回归测试；不适合自动化时说明原因和人工验证方法。
- 不为了让测试通过而修改产品规则，也不删除或弱化失败的测试。
- 只有实际执行且成功的检查才能报告为“通过”；跳过、受阻和失败的检查如实列出。

## Git 与安全

- 不提交密钥、证书、令牌、凭据、敏感数据或本机专属配置；不在仓库里写死本机绝对路径。
- 日志不记录用户内容、凭据、密钥或支付信息。
- 提交保持单一目的，使用 `feat:`、`fix:`、`test:`、`docs:`、`refactor:`、`chore:` 前缀。
- 未经我明确要求，不强推、不改写远程历史、不清理我未提交的修改。
